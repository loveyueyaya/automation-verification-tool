### 2.3 OpenCV（cv2）⚠ 当前存在三包共存冲突

- **核心能力** —— 本项目只用 **6 个 API**：`cv2.imread` / `IMREAD_GRAYSCALE` / `IMREAD_COLOR` / `matchTemplate` / `minMaxLoc` / `absdiff` / `TM_CCOEFF_NORMED`，即"读图 + 模板匹配 + 差分"。
- **能力边界** —— 不认识 UI 语义，只认像素；模板匹配对缩放/字体渲染变化/主题变色极敏感（**这是接入率低的技术根因之一**）；OpenCV 5 的新 DNN 引擎目前 **CPU-only**（GPU 走 Classic 或 ORT）。
- **性能表现** —— `matchTemplate` 经 OpenCL/IPP 优化，1080p 底图 + 100×40 模板约 20–60 ms（**远超 budget 里 locate 的 p95=5ms 目标**，需限制到区域匹配）；cv2 安装体积 **147 MB**。
- **易用性** —— 上述 6 个 API 极简；OpenCV 5 的 breaking change 集中在 DNN/features2d，`matchTemplate` 路径未受影响。
- **生态成熟度** —— CV 领域第一库，GitHub ≈8.6–9.1 万 star，1M+ 日安装。
- **维护状态** —— **非常活跃**：5.0.0 于 **2026-06-04** 发布（pip 版 06-08），是 2018 年以来首个大版本；官方同时维护 4.x/5.x 双线。
- **依赖关系** ⚠ —— 环境当前**同时装了三个包**，都往同一个 `cv2/` 目录写文件：
  - `opencv-python 5.0.0.93`（当前 `cv2.__version__` 实际为 **5.0.0**）
  - `opencv-python-headless 5.0.0.93`（多余）
  - `opencv-contrib-python 4.10.0.84`（**跨大版本污染**，风险最高）
  → 卸载顺序不同会导致 `cv2` 目录残留不同版本的 DLL，是典型的"玄学报错"温床。**建议：卸载 headless 与 contrib，只保留 `opencv-python==5.0.0.93` 并重装校验。**
- **许可证** —— Apache-2.0（含明确专利授权条款），商用友好。
- **底层语言** —— C++ 核心，Python 为自动生成绑定。
- **同类替代** —— ① `skimage.feature.match_template`（更慢）；② numpy 手写归一化互相关约 30 行（可控但无 SIMD 优化）；③ `onnxruntime` + 孪生网络（过度设计）。**结论：保留 OpenCV，但必须解决三包共存。**

| 就绪检测 | `SendMessageTimeoutW`（WM_NULL） | LRESULT 修复已做 ✓ |
| DPI | `GetDpiForWindow` / `GetDpiForSystem` / `SetProcessDpiAwarenessContext` | 必须在进程最早调用 |

- **能力边界** ⚠ —— **UIPI（用户界面特权隔离）**：向更高完整性级别的进程 `SendInput` 会被**静默丢弃**（不报错！），本项目靠 advapi32 预判定并切句柄直投，思路正确；`SetForegroundWindow` 在非前台进程调用会被系统限流（故用 AttachThreadInput）；Wayland 类概念不存在（Windows 无此担忧）。
- **性能表现** —— 单次调用微秒级；`EnumWindows` 全量约 1–10 ms（已有 cache_ttl 缓存 ✓）。
- **易用性** —— ctypes 手写结构体（RECT/POINT/DWORD/HANDLE/LRESULT）坑极多，本项目已被 LRESULT 坑过一次并修复。
- **生态/维护/许可** —— Windows 操作系统组件，**由 Microsoft Update 维护**，许可归 Windows OS 协议：可自由调用，**禁止单独再分发 DLL**。
- **底层语言** —— 原生 Win32（C/汇编）。
- **同类替代** —— ① `pywin32`（已装 312）：`win32gui/win32con` 封装更省心，但多一个依赖与打包体积；② `uiautomation`：更高层，**但不覆盖窗口置顶等 win32 操作**。**结论：保留现有 ctypes 层（已稳定且有 56 测试守护），不再替换。**

#### ② kernel32.dll —— `GetCurrentProcess` / `GetCurrentThreadId` / `CloseHandle`
能力边界：**句柄必须关闭，否则泄漏**（advapi32 那段已用 try/finally ✓）；主线程 ID 用于 AttachThreadInput。`GetCurrentProcess()` 返回伪句柄 -1，无需 Close。许可同 Windows OS。

#### ③ advapi32.dll —— UIPI 判定核心（4 个 API）
`OpenProcessToken` → `GetTokenInformation(TokenIntegrityLevel)` → `GetSidSubAuthorityCount/GetSidSubAuthority` 取末级 SID，映射 high(≥0x4000)/medium(0x2000)/low。
- **能力边界** —— 只**读取**级别，**不提供提权能力**（本项目不寻求自动提权，符合安全预期）；调用失败降级为 medium ✓。
- **性能** —— 单次约 0.1–1 ms，已在 `probe_env` 中带 `probe_ms` 计时并缓存 ✓。
- **替代方案** —— 无必要替代；唯一注意是 `GetTokenInformation` 的 buffer 长度与 SID 结构体抠本级 Folowed guru（本项目用 `cast(byref(buf, sizeof(DWORD)), POINTER(c_void_p))` 取 SID 指针，写法正确）。

#### ④ shcore.dll —— `SetProcessDpiAwareness`
DPI 虚拟化开关；**必须先于此调用才能拿到真实物理像素 rect**，是"坐标一律物理像素"这条契约的前置条件。
- **替代方案** —— 应用清单（manifest）声明 `<dpiAwareness>PerMonitorV2</dpiAwareness>`，打包成 exe 时更稳、**且不需要代码调用**（推荐 P3 打包阶段并行保留两种方式）。

#### ⑤ nvapi64.dll —— `nvapi_QueryInterface`（⚠ 建议删除）
`ocr.py:_setup_gpu` 里 `ctypes.windll.nvapi.nvapi_QueryInterface` 只是摸一下接口存在性，**没有取任何返回值、不影响后续逻辑**，却会尝试加载 nvapi64.dll，在部分机器上慢/失败/被安全软件盯上。**建议：删掉这 3 行，显存探测完全交给 nvidia-smi 或 NVML。**

#### ⑥ gdi32.dll —— 当前未使用
`CaptureMethod.BITBLT` / `PRINT_WINDOW` 两个枚举已定义但无实现。若未来要补"最小窗口 GDI 兜底"，需要 `GetDC/BitBlt/CreateCompatibleDC/PrintWindow`（PrintWindow 对部分自绘窗口返回黑）——**目前不建议补**，mss 的 GDI 就是这条路且已可用，属重复造轮子。

### 2.9 命令行工具 / 外部进程

#### nvidia-smi（subprocess，5s 超时）
- **能力/边界** —— 查询显存总量（当前机器 12,282 MiB），**仅 NVIDIA 驱动可用**；AMD/Intel 与无显卡机器会直接失败降级（代码默认值 12288 MiB ✓）。
- **性能** ⚠ —— **进程启动开销 200–500 ms，且 `load_ocr` 每次调用都会跑一遍**；stdio 服务模式下若多次加载则重复付费。→ **建议把结果缓存到 `contracts/config`（一行 `functools.lru_cache` 即可）**。
- **替代方案** —— ① `NVML`（`nvidia-ml-py`，无进程开销）；② `GPUtil`（**已在 paddlex 依赖声明里但环境未装**）；③ Windows DXGI 查询。**建议保留 nvidia-smi 但加缓存（零依赖，改动最小）。**
- **许可证** —— NVIDIA 驱动附带，不可再分发；调用无限制。

#### taskkill（`subprocess.run(["taskkill","/f","/im",name,"/t"])`）
- 能力边界：进程名匹配会连带杀同名进程；需管理员权限才能杀他人进程。
- **替代方案** —— **psutil 已在项目里**（`psutil.Process.terminate/kill` 更精准、无额外进程开销、跨平台）。→ **建议替换，可少一个外部依赖点。**（同类对比：taskkill 无需安装 vs psutil 更精准，本项目 psutil 已装，选 psutil。）

#### WgcCapture.exe —— ⚠ **缺失的外部二进制**
`shot.py` 期望 `scripts/wgc/WgcCapture.exe`（C# 桥接，Windows.Graphics.Capture），**该目录在磁盘上不存在** → 第一档永远降级。
- **解决路径** —— **不要自研 C#**：`dxcam[winrt]` 已提供原生 WGC 后端（见 §2.5）。自研 C# 需维护 .NET SDK、manifest 权限、进程间 PNG 中转与超时，收益为负。
- **同类对比** —— ① dxcam winrt 后端（推荐，0 行代码）；② `winsdk` / `winrt-Windows.Graphics.Capture` 直接用（约 150 行 Python + 需理解 COM interop）；③ 自研 C# exe（约 300 行 + 构建链，✗）。

### 2.10 Chrome DevTools Protocol（CDP）—— 未实现，P2 必须补

- **核心能力** —— HTTP 端点 `/json/version`、`/json/list`（取每个 target 的 `webSocketDebuggerUrl`）+ WebSocket JSON-RPC 域：`Page.navigate`、`Runtime.evaluate`（取 DOM 文本/执行 JS）、`Input.dispatchMouseEvent`/`dispatchKeyEvent`、`DOM.getDocument`/`getBoxModel`。

| 候选 | 最后更新 | 依赖 | 适配度 | 结论 |
|---|---|---|---|---|
| **websocket-client** | 持续维护，广泛使用 | 纯 Python | ⭐⭐⭐⭐⭐ 同步、轻量、贴合本项目命令式风格 | **首选**（pychrome 底层即它） |

### P1 · UIPI 导致 SendInput **静默失败**（无异常、无日志）

- **现象预判**：向更高完整性级别进程注入时，SendInput 被内核静默丢弃，返回值看不出问题；UIA 跨 IL 同样被阻断。
- **联网方案**：
  1. **Microsoft 官方工具文档（winapp-cli）明确写道**：`post-message`（即 `PostMessageW`）**绕过 UIPI 且不依赖目标为前台窗口**，是默认传输方式；`send-input` 走系统输入队列、受 UIPI 限制；并指出 post-message 的两个边界：不能触发低层键盘钩子注册的热键、WinUI3/UWP 无子 HWND 时投递会被丢弃。
  2. 社区实践推荐回退链：**UIA ValuePattern → SendInput → 剪贴板注入**（剪贴板访问不受 UIPI 约束，Ctrl+V 走全局键盘队列可达高 IL 窗口）。
  3. 其他提示：目标进程可能注册 raw/DirectInput 忽略传统消息；`LLKHF_INJECTED` 标志可被对方识别并丢弃。
- **可行性评估**：✅ 完全可行且**本项目已具备其中两档**（`sendinput.py` 已有 SendInput + `post_key/post_char` + `paste_at` 剪贴板粘贴）。
- **本地实测**：`probe_env` 返回本机 `integrity=medium`（非管理员运行），`input_router` 在低完整性时已自动切 `handle_post` —— **逻辑已正确**。
- **处置**：`input_router` 增加两条规则：① 本机 medium + 目标 high → 强制 `handle_post`；② `handle_post` 失败 → `paste_at`（剪贴板）兜底。约 10 行。

### P2 · 远控 / 安全软件环境输入被拦截 —— **本机已真实发生**

- **实测**：`_remote_software()` 返回 `'wujie'`，命中进程 **`wujie.exe`（真阳性，非误报）**；`probe_env` 输出 `focus_reliable=False`，`input_router → handle_post`，`capture_router → mss`。
- **联网方案**：与本项目的三类注入（SendInput / 句柄直投 / WM_CHAR）完全对齐；业界对这类环境的通用做法就是"放弃全局输入、改窗口消息直投"。
- **⚠ 但实测同时暴露误伤（BUG-4）**：`probe_env` 中 `framework` 字段被**全局**安全软件检测结果污染——目标窗口进程明明是 `360se.exe`，却被标成 `framework=wujie`，于是本该走 `native` 的浏览器被整体降级（截图 0.04ms → 17.08ms，**慢 427 倍**）。
- **处置**：`framework` 只按**目标窗口所属进程**判定；远程软件只写入 `security` / `focus_reliable`。这是本次盘点评级最高的修复项之一。

### P3 · DPI 缩放与多屏坐标错位

- **联网方案**：
  1. 必须在进程最早调用 `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`（值 **-4**），之后 `GetWindowRect` 返回真实物理像素；代价是要自己处理 `WM_DPICHANGED`。
  2. 用 `GetDpiForWindow(hwnd)`（Win10 1703+）替代过时的 `GetDpiForMonitor`；逻辑/物理互转应使用 **`PhysicalToLogicalPointForDpi` / `LogicalToPhysicalPointForDpi`** 这一对函数，而不是简单乘缩放比（多篇资料里的"乘 scale"写法在跨屏时会错）。
  3. 多屏注意**负坐标**（副屏在主屏左上时坐标为负）—— 本项目实测已见到 `rect=(-9,-9)-(2055,1111)`，属正常现象，裁剪逻辑需按虚拟桌面包围盒做 `Intersect`。
- **本地实测**：`env.py` 已使用 `c_void_p(-4)` + 回退 `shcore.SetProcessDpiAwareness(2)`，并用 `GetDpiForWindow` —— **已符合业界最佳实践**；本机 100% 缩放，无法复现错位。
- **处置**：① 补 `PhysicalToLogicalPointForDpi` 互转（约 15 行）；② 在 125%/150% 目标机上补一次回归验证（**本机无法复现，不谎称已验证**）。

### P4 · OCR 误识别率 —— 已量化

- **实测**（全屏 2560×1440 真实桌面，PP-OCRv6_medium）：识别 **179 条**，其中 **confidence < 0.8 的有 20 条（11.2%）**；conf<0.6 的垃圾样例包括 `'杰'(0.12)`、`'關'(0.166)`、`'F'(0.438)`、`'0.'(0.438)`、`'8'(0.365)` —— 全是图标、边角、纯噪声。
- **联网方案（PaddleOCR 官方 FAQ）**：
  - 精度：`PP-OCRv5_server` 系列最高精度；`PP-OCRv5_mobile` 最快；多语言用 `PP-OCRv5_multi_languages`。
  - 速度：`enable_hpi=True`、`use_tensorrt=True`（需 CUDA11.8+/TRT8.6+）、`precision="fp16"`、调 `batch_size`、换 mobile 模型。
  - OOM：`batch_size=1`、`det_limit_side_len=640`、`enable_memory_optim=True`、`gpu_mem=200`。
- **可行性**：精度类建议 ✅（换模型档位即可）；速度类**需实测**（见 P5）。
- **处置（自研部分，极薄）**：
  1. `OcrItem.confidence` 阈值过滤（本项目 `contracts.models.OcrItem` **已有 confidence 字段，但 ocr.py 未设过滤门槛**）→ 加 `min_conf=0.6`（约 2 行）；
  2. 用 `--filter` 目标子串 + `contracts.state_hash.normalize_text`（已有）做归一化后再比对；
  3. **绝不把 OCR 结果当坐标来源**（`SourceEnum` 设计已守住这条底线 ✅）。

### P5 · OCR 性能与官方调优参数 —— 实测有真有假

| 配置 | 加载 | 裁剪推理(稳态) | 全屏推理 | 显存 | 结论 |
|---|---|---|---|---|---|
| baseline（现项目参数） | 7,277 ms | **11.9 ms** | **1,203 ms** | 4,080 MiB | 基准 |
| `+precision=fp16` | 1,043 ms | **9.7 ms** | **916 ms（-24%）** | 4,037 MiB | ✅ **有效，建议采纳** |
| `+enable_hpi=True` | — | — | — | — | ❌ **RuntimeError: Engine 'hpi' 不可用，缺依赖 `ultra-infer`** |
| `+det_limit_side_len=640` | 989 ms | 143.0 ms ⚠ | 926 ms | 4,590 MiB | ⚠ **数据反常（稳态反而变慢），参数名需复核，暂不采纳** |

- **结论**：官方 FAQ 的三条提速建议里，**只有 fp16 本机直接可用**；`enable_hpi` 需要额外装 `ultra-infer`（体积与离线分发成本需权衡，P3 阶段再评估）；`det_limit_side_len` 组数据不可信，需重测后再决定。
- **最大的一笔收益不来自参数，而来自调用方式**：常驻 `--serve` + 限定区域 = **10,970 ms → 52 ms（210×）**（见 §3.0）。参数调优只能再省 24%。**先修调用方式，再谈参数。**

### P6 · 显存挤占

- **实测**：基线 2,346 MiB（其他程序占用）→ OCR 加载推理后 4,080 MiB，**增量约 1,734 MiB**；而 `ocr.py` 设置的上限是 9,825 MiB（12,282×0.8）。
- **联网方案**：官方 FAQ 提供 `gpu_mem=200`、`enable_memory_optim=True`、`batch_size=1` 等收紧手段。
- **处置**：80% 上限过于宽松且用的是 `FLAGS_gpu_memory_limit_mb` 环境变量（paddle 3.x/PaddleX 时代更推荐 `device` + `precision` 等显式参数）。建议：① 上限改为**实测峰值 ×1.5（约 2,600 MiB）**；② 把 GPU 信息探测结果（现由 nvidia-smi 提供）缓存起来。

### P7 · 截图黑屏 / DXGI 瞬断

- **联网方案**：
  1. dxcam 同类项目给出的故障表：DPI≠100% → 自动回退 mss；**黑屏/空帧 → GPU 资源冲突（关闭 OBS 等录屏软件）**；启动崩溃 → 需 DirectX 11+；0×0 → 未检测到显示器。
  2. DXGI 黑屏/闪烁根因：`AcquireNextFrame` 后**未及时 ReleaseFrame** 导致资源锁死；多进程同时桌面复制更易触发。另有 Windows **DCI Timeout 注册表（默认 7s）** 在高负载下强制返回黑屏帧，社区方案是设为 0（**需谨慎，属系统级改动**）。
- **可行性**：✅ 前两条本项目天然满足（单进程、用完即 `close()`；且有 mss 兜底）。
- **本地实测**：`shot.py` 实跑正常（dxcam 单帧 0.04ms），未出现黑屏；但本机因 wujie 判定已走 mss。
- **处置**：保持"WGC > dxcam > mss"三级降级；**不建议改注册表**（离线工具不应要求改用户系统配置）；若在目标机复现黑屏，处置顺序为：关录屏软件 → 强制 mss → 记录 `ENV_UNSUPPORTED` 走降级表。

### P8 · OpenCV 三包共存冲突 —— 官方定论

- **联网方案**：OpenCV 官方与多个权威来源一致表述：**"Never install more than one of these at the same time. They conflict."** 四个包共用 `cv2` 命名空间、没有插件架构；正确做法是**全部 uninstall 后只装一个**。
- **本地实测**：环境同时存在 `opencv-python 5.0.0.93` + `opencv-python-headless 5.0.0.93` + `opencv-contrib-python 4.10.0.84`，`cv2/` 目录 147MB。
- **处置**：项目只用 6 个 core/imgproc API，**不需要 contrib** → 卸载 headless 与 contrib，保留并重装 `opencv-python==5.0.0.93`，跑 `python -c "import cv2; print(cv2.__version__, cv2.__file__)"` 校验。

### P9 · cuDNN 版本不符

- **实测**：`pip check` → `paddlepaddle-gpu 3.3.1 requires nvidia-cudnn-cu12==9.5.1.17, but you have 9.9.0.52`；但实测 `paddle.device.is_compiled_with_cuda()=True` 且能读到 RTX 4080 Laptop 设备属性（算力 8.9）—— **能跑，但不在官方保修范围**。
- **联网方案**：官方 FAQ 给出 CUDA 版本 ↔ paddle 版本对应表，并建议用 `nvidia-smi` 先确认 CUDA 版本再选 paddle 版本。
- **处置**：**不要执行 `pip install -U`**（会把 paddle 连带升到不确定的组合）。把当前组合写进 `10-env-baseline`，并在打包时锁定 `nvidia-cudnn-cu12==9.9.0.52` 现状。

### P10 · Chromium 页面内容 UIA 全不可见 —— 实测 + 搜索双重确认

- **本地实测**：对 360 安全浏览器（Chromium 内核）窗口做 UIA 遍历，depth≤3 **只拿到窗口外壳**（TitleBar/Pane/窗口本身），**页面控件 0 个**。
- **联网方案与关键约束**：
  1. 加 `--force-renderer-accessibility` 才能开启页面级 UIA —— **但 Blue Prism 官方文档与社区一致指出：若浏览器已在运行，该参数无效，必须重启浏览器进程**；同时该参数会**立即启用 UIA，带来较高 CPU 开销**。
  2. 不加参数时，浏览器会等到"检测到读屏软件访问 UIA 桥"才启用 → **首次访问必然失败，后续可能成功**（这解释了实测现象）。
  3. 也可用 `chrome://accessibility/` 手动为指定页面开启。
  4. 业界共识：**页面内容优先 CDP/DOM，UIA 只用于外壳**——与本项目需求 §2 的分流定义一致。
- **对本项目的可行性判断**：cookie_sync **已经开着浏览器**，加参数需重启被测程序 → 属于业务处置（可能丢失登录态/会话），因此**必须自研一个"是否值得重启浏览器"的策略决策**（即 §3.3 第 4 项）。
- **处置**：① 页面内容一律走 CDP（Wave 4）；② `env_adapter` 只输出"建议"，由 orchestrator 决定是否重启被测程序；③ UIA 重试策略改为**首次失败后重试 1–2 次**（对应"桥接启用延迟"），约 10 行。

### P11 · 模板匹配对缩放极敏感 —— 实测量化

| 场景 | 最高相关系数 |
|---|---|
| 原图自匹配 | **1.0000** |
| 缩放 **0.90×** | **0.7565**（跌破常用 0.8 阈值 ❌） |
| 缩放 0.95× | 0.9104 |
| 缩放 1.05× | 0.9238 |
| 缩放 1.10× | 0.8181 |
| 亮度 ×0.8 / ×0.9 / ×1.1 | 0.9985 / 0.9987 / 0.9991（几乎无影响 ✅） |
| 轻微模糊（渲染差异） | 0.9884（几乎无影响 ✅） |

- **联网/通用方案**：多尺度模板匹配（multi-scale template matching）—— 实测有效但代价高。
- **本地实测（代价）**：
  - 全屏多尺度 15 档 ≈ **374 ms**（24.9×15）
  - **限定区域 250×170 多尺度 15 档 = 7.47 ms**（比全屏快 **50×**），且能把 0.90× 场景的相关系数从 0.7565 救回 **0.9874**

- **处置**：`locate.py` 增加 `scales` 参数，**只在传入 bbox 区域时启用多尺度**，并限制档位（0.9/0.95/1.0/1.05/1.1 五档 ≈ 2.5 ms）。约 20 行。

### P12 · 跨进程 trace 时钟对齐

- **联网方案（OpenTelemetry 业界模型）**：
  1. 正确实现是**用单调时钟算耗时、用墙钟记时刻**（naive 实现用墙钟相减，会因 NTP 回拨产生负耗时）；
  2. 时钟偏移（clock skew）在跨主机场景靠 NTP；**单主机跨进程靠 offset 校准**；
  3. 上下文传播用 trace_id/span_id/parent_span 三元组（W3C traceparent 思路）；孤儿 span（无父）是已知的"断链"征兆。
- **本地实测**：`timeline.py` **已经在用 `perf_counter`（单调）算 delta、用 `time.time()` 记墙钟** —— 与业界推荐一致 ✅；`uitool.py` 有 **8 处 `_sub()` 子进程调用，均未传 `--trace-id`**（详细设计里写的是"约 6 处"，实测为 8 处）。
- **处置**：① `contracts.models.TraceSpan` 补 `span_id`/`parent_span`（详细设计已定）；② 8 处 `_sub()` 加 `--trace-id` 透传；③ 报告层做孤儿 span 标黄。**无需引入 OTel SDK**（进程内/子进程场景太重，自有 3 个字段即可）。

def bfs(root, max_depth=3):
    q, n, named, samples = deque([(root, 0, ())]), 0, 0, []
    while q:
        c, d, pre = q.popleft(); n += 1
        name = (c.Name or "").strip()
        if name: named += 1
        if name and len(samples) < 5: samples.append(name)

    return n, named, samples

### 3.1 事故与根因（全链路实测，非推断）

**已排除**（均实测）：磁盘空间、杀软隔离（系统未注册杀软、Defender cmdlet 不存在）、沙箱 GC（仅"无需删除"172 次）、CLI 文件树清单回滚（只覆盖工作区）、凭据检测规则。

4. **一切判断基于实测**：文件/包存在性用 `os.path.exists` / `importlib.util.find_spec` / 实跑验证，不得用 RECORD、README、索引描述替代。
5. **审计保留**：系统文件系统审核 + `C:\Program Files\Python313` 的 Delete SACL 长期保留，可随时归因删除进程（回滚命令见 root-cause 报告 §2.3）。
6. **版本问题处理**：查官方手册/更新说明；不涉及本项目实际调用 API 则不做升级。
