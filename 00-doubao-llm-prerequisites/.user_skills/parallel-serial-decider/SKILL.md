# 并行/串行判定规范 v2.0

适用：所有由豆包执行的任务
生效：立即
维护：每次归类错误后更新规则表，记录版本
变更：v2.0 新增临时缓存、决策日志、三级策略、回滚协议

## 一、核心原则

1. **规则优先，不靠感觉**
   - 从任务描述中提取关键词
   - 用关键词匹配规则表
   - 按规则表执行
   - 匹配不到 = 默认串行

2. **三级策略**：并行 > 谨慎 > 串行，命中多条取最严格

3. 每次任务前必须输出"并行判定"，不输出判定 = 违规

4. 不确定时：
   - 先查决策日志（见第五节）看有没有同类案例
   - 没有 → 默认串行 + 创建临时缓存
   - 不许自己猜

5. 用户指令 > 规则表：用户强制并行时，必须先警告风险，等用户确认

6. 任何可能改坏的操作，先建临时缓存，改错能一键回滚

## 二、三级策略定义

| 策略 | 允许范围 | 适用场景 | 风险 | 缓存要求 |
| --- | --- | --- | --- | --- |
| **并行 Parallel** | 多个任务同时执行 | 只读、写不同文件、无依赖 | 可控 | 不需要 |
| **谨慎 Cautious** | 允许并行，但每步完成后停下报告 | 写不同文件但共享 git / 磁盘 / 缓存 | 中等 | 必须搭配临时缓存 |
| **串行 Serial** | 严格按顺序执行，每步验证后再进下一步 | git 写操作、有依赖、改同一资源、不确定 | 大 | 必须搭配临时缓存 + 回滚点 |

## 三、判定流程

1. 从任务描述提取关键词
2. 在规则表中匹配
3. 命中即执行对应策略；命中多条取最严格
4. 未命中任何规则 → 查决策日志
   - 4a. 日志有同类案例 → 按日志策略执行
   - 4b. 日志无案例 → 默认串行 + 创建临时缓存
5. 输出"并行判定"（格式见第七节）
6. 执行前建临时缓存（如果策略是谨慎/串行）
7. 按判定执行
8. 执行后写决策日志（见第六节）

## 四、规则表

| 编号 | 关键词（命中任一） | 策略 | 理由 |
| --- | --- | --- | --- |
| R1 | 只读 / 查询 / 查看 / 统计 / 列出 / status / log / ls / cat / findstr | 并行 | 不写数据 |
| R2 | 搜索 / grep / Select-String / 匹配 | 并行 | 只读 |
| R3 | 写不同文件 / 生成A和B / 同时输出X Y | 并行 | 资源不冲突 |
| R4 | 打包 + 写说明 / 压缩 + 生成文档 | 并行 | 不同资源 |
| R5 | 跑测试 + 写文档 / 测试 + 分析 | 并行 | CPU与IO不同 |
| R6 | git commit / git push / git tag / git branch / git merge / git mv / git rebase / git reset / git checkout | 串行 | git有index.lock |
| R7 | 改分支名 / 重命名分支 / 删分支 | 串行 | 引用变化 |
| R8 | 打tag + 建release / tag和release一起 | 串行 | release依赖tag |
| R9 | 拆目录 / 重命名目录 / 移动文件 | 串行 | import路径会断 |
| R10 | 改import / 改模块引用 / 重构 | 串行 | 依赖链 |
| R11 | 改同一文件两次 / 追加再修改 | 串行 | 后写覆盖前写 |
| R12 | 改config / 改配置 + 重启 / 改yaml + reload | 串行 | 读到半个文件 |
| R13 | 迁移 + 验证 / 改造 + 测试 | 串行 | 测试基于旧路径 |
| R14 | 打包 + 上传 / 压缩 + push | 串行 | 上传依赖打包 |
| R15 | 跑多个git命令 | 串行 | 锁冲突 |
| R16 | 不确定 / 可能 / 大概 / 应该 / 也许 | 串行 | 保命原则 |
| R17 | 部署 / 发布 / 上线 / 回滚 | 串行 | 状态敏感 |
| R18 | 数据库 / 写文件 / 追加日志到同一文件 | 串行 | 写锁 |
| R19 | 依赖前面结果 / 用上一步的输出 | 串行 | 有依赖 |
| R20 | 外部API调用 + 写文件 / 下载 + 解压 | 串行 | 顺序依赖 |
| R21 | 写多个文件但共享git / 共享缓存 / 共享磁盘 | 谨慎 | 可能冲突 |
| R22 | 批量操作 / 批量重命名 / 批量替换 | 谨慎 | 面广风险高 |
| R23 | 跨目录操作 / 跨模块操作 | 谨慎 | 影响范围大 |

## 五、决策日志

目的：让豆包快速查找历史决策，不用每次重新思考。

### 日志位置

`F:\自动化验证工具\00-doubao-llm-prerequisites\.user_skills\parallel-serial-decider\decision-log\decisions.jsonl`

### 日志格式（每行一条 JSON）

```json
{
  "ts": "2026-09-16T22:30:00",
  "task": "改分支名 + 写文档",
  "keywords": ["改分支名", "写文档"],
  "hit_rules": ["R7", "R3"],
  "final_strategy": "serial",
  "reason": "R7 最严格，取串行",
  "cache_created": true,
  "cache_path": "F:\\自动化验证工具\\临时缓存\\20260916_223000",
  "result": "success",
  "duration_s": 12.5,
  "notes": ""
}
```

### 使用方式（每次任务前必查）

1. 提取关键词
2. 读 decisions.jsonl
3. 搜索相同关键词的最近 3 条
4. - 有成功案例 → 按案例策略
   - 有失败案例 → 用案例里失败的反面策略
   - 无案例 → 走规则表

### 写入时机

每次任务完成后立即写入，不许拖延。

### 日志滚动

- 单文件超过 10MB 时归档为 decisions_<日期>.jsonl
- 保留最近 30 天

## 六、临时缓存机制

目的：改错了能一键回滚，不丢代码。

### 触发条件

以下任一命中，执行前必须建缓存：
- 策略是"谨慎"或"串行"
- 涉及 git 写操作（commit / push / mv / branch / reset / rebase）
- 涉及目录重命名、文件移动
- 涉及改 import / 重构
- 涉及配置修改
- 用户要求"安全操作"

### 缓存位置

`F:\自动化验证工具\00-doubao-llm-prerequisites\.user_skills\parallel-serial-decider\temp-cache\<时间戳>\`

目录结构：

```
temp-cache/
├── 20260916_223000/
│   ├── snapshot/                ← 完整复制
│   │   ├── 04-implementation/
│   │   └── config/
│   ├── git_state.txt            ← git branch / git log -1 / git status
│   ├── manifest.json            ← 快照元数据
│   └── restore.ps1              ← 一键恢复脚本
```

### manifest.json 格式

```json
{
  "ts": "2026-09-16T22:30:00",
  "task": "改分支名 + 目录重命名",
  "strategy": "serial",
  "snapshot_of": ["04-implementation", "config"],
  "git_branch": "main",
  "git_commit": "05ab9fc",
  "restore_cmd": "powershell -File restore.ps1"
}
```

### 自动清理

- 成功后：保留 7 天，自动清理
- 失败后：保留 30 天，防止问题复发
- 手动清理：用户说"清理缓存"时清空

### 使用场景

1. 操作前：豆包自动建缓存
2. 操作后：验证通过 → 标记 success
3. 操作后：验证失败 → 用户说"回滚"，豆包执行 restore.ps1
4. 回滚后：写决策日志，标记 failed + rollback

## 七、执行格式（每次任务开始前必须输出）

```
【并行判定】
任务1：<描述> → 命中 R<编号> → <策略>
任务2：<描述> → 命中 R<编号> → <策略>
命中多条：<列出编号>
最终策略：<并行 / 谨慎 / 串行>
执行顺序：<串行时列出步骤>
理由：<一句话>

【缓存判定】
是否需要缓存：<是 / 否>
缓存理由：<命中 R 编号或触发条件>
缓存路径：<如果建缓存，填路径>

【日志查询】
历史同类任务：<有 / 无>
历史策略：<查到的策略>
本次策略：<是否与历史一致>
```

示例：

```
【并行判定】
任务1：改分支名 → 命中 R7 → 串行
任务2：写需求文档 → 命中 R3 → 并行
命中多条：R7, R3
最终策略：串行（取最严格）
执行顺序：
  1. 改分支名（含缓存）
  2. 写需求文档
理由：R7 是 git 写操作，必须串行

【缓存判定】
是否需要缓存：是
缓存理由：命中 R7（改分支名）
缓存路径：F:\自动化验证工具\临时缓存\20260916_223000\

【日志查询】
历史同类任务：有（2026-09-15）
历史策略：串行
本次策略：一致
```

## 八、违规示例

| 违规 | 正确做法 |
| --- | --- |
| 1. 把"改分支名 + 写文档"全并行 | 串行（R7） |
| 2. 把"打tag + 建release"并行 | 串行（R8） |
| 3. 把"拆目录 + 跑测试"并行 | 串行（R13） |
| 4. 把"改分支名 + push"并行 | 串行（R6+R15） |
| 5. 把"两个git mv"并行 | 串行（R6+R15） |
| 6. 把"边改代码边跑测试"并行 | 串行（R13） |
| 7. 把"压缩 + 上传"并行 | 串行（R14） |
| 8. 不确定能不能并行直接当并行 | 串行 + 缓存（R16） |
| 9. 未输出"并行判定"直接执行 | 先输出判定，再执行 |
| 10. 命中多条规则时拍脑袋选并行 | 取最严格，串行 |
| 11. 串行操作未建缓存 | 串行必须先建缓存 |
| 12. 操作后未写决策日志 | 每次任务完成后立即写日志 |
| 13. 不确定时未查决策日志 | 先查日志，再决定 |

## 九、回滚协议

### 用户说"回滚"时：

1. 读取最近一次缓存的 manifest.json
2. 执行 restore.ps1
3. 验证恢复结果（对比 snapshot 与当前状态）
4. 写决策日志，标记 failed + rollback
5. 报告：恢复了什么、从哪个时间点

### 用户说"回滚到 N 小时前"时：

1. 列出最近 N 小时内的所有缓存
2. 让用户选一个
3. 按上面流程执行

### 用户说"清理缓存"时：

1. 列出所有缓存目录
2. 让用户确认哪些可删
3. 删除后写日志

### 回滚必须满足：

- 缓存存在且完整
- git 状态允许回滚（没有未提交的冲突）
- 用户明确确认

### 回滚失败时：

- 不删缓存
- 报告失败原因
- 让用户手动处理

## 十、边界情况处理

**情况1：任务不在规则表中**
1. 先查决策日志
2. 日志有同类 → 按日志
3. 日志无同类 → 问用户："任务 XXX 不在规则表，日志也无案例。请确认：A. 并行（我建缓存）B. 谨慎（我建缓存，逐步做）C. 串行（我建缓存，严格按顺序）"

**情况2：任务跨多类**
取最严格策略。部分可并行部分串行 → 拆成阶段：
- 阶段1（并行）：...
- 阶段2（串行 + 缓存）：...

**情况3：用户强制并行**
必须警告："用户要求并行，但任务命中 R<编号>。风险：<具体>。建议：A. 改串行（安全）B. 坚持并行 + 建缓存（出错可回滚）。请确认。"

**情况4：同一消息多个任务**
逐条判定，汇总。部分并行部分串行 → 按阶段拆。

**情况5：决策日志里查到失败案例**
- 取失败案例的反面策略，或直接问用户
- 不许盲目重复失败策略

## 十一、规则表维护

1. **新增场景**：规则表未覆盖 → 用户提供判定 → 加入规则表 → 更新版本
2. **归类错误**：用户说"这次归类错了，正确是XXX" → a. 案例加入违规示例 b. 新关键词加入规则表 c. 更新 SKILL.md 版本
3. **决策日志分析**：每 10 次任务后，豆包主动统计：哪些策略最常用、哪些任务经常出错、是否需要新增规则
4. **版本记录**：每次规则表变更，记录版本号、日期、变更内容、变更原因

## 十二、常驻口令

从现在开始，所有任务必须按"并行/串行判定规范 v2.0"执行。强制要求：

1. 任务开始前必须先输出"并行判定"+"缓存判定"+"日志查询"三块
2. 未输出判定 = 违规
3. 命中多条取最严格
4. 匹配不到 = 查日志 → 无案例则串行 + 建缓存
5. 关键词来自任务描述，不许"我觉得"
6. 不确定时查日志，日志无则问用户
7. 谨慎/串行任务必须先建临时缓存
8. 任务完成后立即写决策日志
9. 用户强制并行时，先警告风险，等确认
10. 用户说"回滚"时执行 restore.ps1

违反任一条，用户有权打回重做。
