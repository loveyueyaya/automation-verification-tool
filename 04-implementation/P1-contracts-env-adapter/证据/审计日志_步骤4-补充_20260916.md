## 任务三结论（正式回答）

**AppData 部分被清、pyc 保留的机制**

可观察事实（已验证）：
- 被清：`...\Default\.doubao\agent_mode\workspace\.user_skills\ui-toolbox\`（技能源码/工作区）
- 保留：`...\sandbox_runtime\.cache\python\pyc-cache\...\ui-toolbox\`（运行时字节码缓存）

机制解释（区分事实与推断）：
1. **两个目录属于不同子树/清理域**：
   - `Default\.doubao\agent_mode\workspace` = 会话工作区 + 技能源码域
   - `sandbox_runtime\.cache\python\pyc-cache` = 运行时字节码缓存域（与 Default 平级）
   你手动清空 AppData 时，清理范围覆盖了 workspace 技能源码区，未覆盖 sandbox_runtime 缓存区。
2. **pyc 是孤儿缓存**：pyc-cache 等价于 Python 的 `__pycache__` 机制，解释器运行时按需生成；源码目录被删**不会**自动删除已生成的 pyc（孤儿保留）。这是"源没了、缓存还在"的直接原因。
3. **诚实边界**：豆包客户端内部清理调度器的精确触发条件（何时/何操作触发清理）属产品内部机制，我无法从外部验证，**不编造**。事实性风险：**任何针对 `sandbox_runtime\.cache` 的清理动作（客户端缓存清理、磁盘清理工具、手动删除）都会删除 pyc**。
4. **如何保证项目代码永不依赖 AppData**（已落地 + 进行中）：
   - 权威源已迁移 F 盘（contracts / env_adapter / scripts / tests / MIGRATION.md），SKILL.md 已加"项目代码权威源 F 盘，禁止写 AppData"声明
   - pyc 仅作一次性恢复参考，不承担运行依赖
   - 你的 F 盘备份（P1_pyc缓存备份_20260916）为最后保险
